# Benchmark RAG

Набор для одинаковой проверки каждой версии поиска и ответов.

## Состав
| Что | Где | Объём |
|---|---|---|
| Корпус | [`../corpus/D01.md … D30.md`](../corpus) | 30 документов (D01–D10 — карточки коворкингов из `frontend/data.js`, D11–D30 — правила, цены, услуги). Все данные вымышленные. Один документ = один фрагмент. |
| Вопросы | [`questions.json`](questions.json) | 10 обычных (Q01–Q10, у каждого ≥ 3 релевантных документа, эталон и ключевые факты `must_include`) + 5 ловушек (T01–T05, ответа в корпусе нет — ожидается «В документах нет этой информации.») |
| Прогон | [`run.py`](run.py) | считает метрики и сохраняет выдачу и ответы по каждому вопросу |
| Результаты | [`results/`](results) | `<tag>.json` (всё по каждому вопросу) и `<tag>.md` (таблицы + ответы) |

Темы вопросов: часы работы, переговорные, цены, парковка, печать, отмена и возврат, команды, скидки, ранний старт, тихие зоны.

## Как запустить
Из корня репозитория, зависимости не нужны (только Python 3.10+):

```bash
python benchmark/run.py --compare                    # сравнить версии поиска
LLM_MODE=extractive python benchmark/run.py          # офлайн, без нейросети
LLM_API_KEY=sk-... LLM_MODEL=gpt-4o-mini python benchmark/run.py --tag llm   # с настоящей LLM
```
Для локальной модели: `LLM_BASE_URL=http://localhost:11434/v1 LLM_MODEL=qwen2.5:7b python benchmark/run.py --tag ollama`.

## Договорённости о метриках
- **k = 5**: в контекст LLM передаём top-5. Recall считаем на @3 и @5, MRR — на глубине 5 (нет релевантного в top-5 → RR = 0).
- **Метрики поиска** — только по 10 обычным вопросам; ловушки в них не входят.
- **Accuracy** — доля обычных вопросов, где ответ не отказ и содержит все ключевые факты эталона (`must_include`, без учёта регистра; «1 200» = «1200»). Автопроверку стоит подтвердить глазами по `results/<tag>.md`.
- **Correct Rejection Rate** — доля ловушек, на которые система ответила отказом.
- Сравнивая версии, меняем одну настройку за раз: тот же корпус, те же вопросы, та же глубина k.

## Разбор ошибок
Где потеряли информацию: в базе → в поиске → в контексте → в ответе.

**Поиск (база в порядке, текст есть):**
- **Q05** «Где можно *распечатать* документы…» — Recall@5 = 0.2. В D21 слово «печать», в карточках — «принтер»; «распечатать» → основа «распечат» ≠ «печат». Тот же случай, что «вернуть деньги ≠ возврат оплаты»: BM25 не видит синонимов и однокоренных слов с приставкой.
- **Q01** «…работают после 22:00?» — второе место у D03 («Смена», Петербург, 08:00–**22**:00): совпали числа «22» и «00». BM25 не понимает условий по времени и городу; D02 («круглосуточно») не найден по словам вопроса.
- **Q07** «команде из 10 человек» — в top-5 попали D05 и D10 («до 8 человек»): слова «команд» и «человек» есть почти в каждой карточке, число «10» тоже частое. Ограничение «≥ 10» поиск не проверяет.
- **Q08** — D14 не найден: «студенческий» → «студенческ» ≠ «студент» (наш стеммер слишком простой).
- **Q09** — D04 и D10 не найдены: в карточках «Часы работы: 09:00…», а в вопросе «открывается раньше всех».

**Ответ (заглушка без LLM):**
- **Q02, Q07** — ложный отказ: правило отказа требует, чтобы ≥ 75% значимых слов вопроса встречались в найденном тексте, а слов «поработать», «дороже», «подойдёт» в корпусе нет.
- **Q01, Q03, Q05** — заглушка берёт максимум 4 предложения и не проверяет условия (город, цену), поэтому часть фактов теряется или попадает лишнее. Это задача для LLM.

**Что пробовать дальше (по одной настройке):** лемматизация вместо простого стемминга (pymorphy3), синонимы в запросе («распечатать → печать, принтер»), подбор k1/b, k = 3 vs 5, обязательный прогон с LLM.
