# Спецификация RAG-модуля CoworkingFinder

## 1. Назначение RAG-модуля

RAG (Retrieval-Augmented Generation) — технология генерации ответов с использованием информации, предварительно найденной во внешнем источнике данных.

В проекте CoworkingFinder RAG-модуль предназначен для интеллектуального поиска и подбора коворкингов на основании запросов пользователя на естественном языке.

Основная задача модуля — предоставить пользователю возможность описать требования к рабочему пространству в свободной форме и получить рекомендации подходящих коворкингов с объяснением причин выбора.

Например, пользователь может отправить запрос:

«Найди коворкинг в Москве стоимостью до 800 рублей в день, с Wi-Fi и переговорной комнатой».

Система должна найти документы, содержащие сведения о подходящих коворкингах, и сформировать ответ на основании найденной информации.

В отличие от обычной фильтрации по отдельным параметрам, RAG-модуль позволит обрабатывать текстовые запросы, содержащие несколько требований одновременно.

## 2. Основные компоненты RAG

RAG-модуль будет состоять из следующих компонентов:

**Корпус документов** — набор текстовых документов, содержащих информацию о коворкингах.

**BM25** — алгоритм информационного поиска, предназначенный для определения релевантности документов пользовательскому запросу.

**LLM (Large Language Model)** — большая языковая модель, используемая для формирования текстового ответа на основании найденных документов.

**Модуль формирования контекста** — компонент, объединяющий найденные документы и пользовательский запрос для передачи языковой модели.

**Модуль обработки ответа** — компонент, обеспечивающий возврат сформированного ответа на серверную часть приложения.

## 3. Корпус документов

Корпус документов является основным источником информации для RAG-модуля.

В рамках проекта планируется сформировать набор документов с описаниями коворкингов.

Каждый документ должен содержать информацию об отдельном рабочем пространстве.

Основные сведения, которые предполагается включать в документы:

- Название коворкинга.
- Город и район расположения.
- Адрес.
- Стоимость посещения.
- График работы.
- Доступные удобства.
- Наличие переговорных комнат.
- Условия посещения и бронирования.
- Дополнительное описание рабочего пространства.

Каждому документу будет присвоен уникальный идентификатор, позволяющий сопоставить найденную информацию с конкретным коворкингом.

На начальном этапе допускается использование подготовленного учебного набора данных. В этом случае все вымышленные сведения должны быть обозначены как демонстрационные.

В текущей версии CoworkingFinder информация о коворкингах хранится в файле `frontend/data.js`. В дальнейшем эти данные могут использоваться как основа для подготовки текстового корпуса.

Перед использованием документы должны быть приведены к единому формату.

## 4. Подготовка и индексация документов

Для обеспечения поиска необходимо выполнить предварительную обработку корпуса документов.

Подготовка данных будет включать:

1. Сбор информации о коворкингах.
2. Приведение документов к единой структуре.
3. Очистку текстовых данных от лишних символов.
4. Разделение текста на отдельные слова.
5. Подготовку данных для построения поискового индекса.
6. Создание индекса BM25.

При обработке текстов необходимо учитывать особенности русского языка.

В частности, слова в пользовательских запросах и документах могут встречаться в различных грамматических формах.

Для повышения качества поиска может применяться нормализация текста, включая приведение слов к нижнему регистру и использование лемматизации.

Выбранные методы предварительной обработки должны одинаково применяться к документам и пользовательским запросам.

После подготовки корпуса будет построен поисковый индекс, используемый алгоритмом BM25 для ранжирования документов.

## 5. Поиск документов с использованием BM25

BM25 — алгоритм ранжирования документов по степени их соответствия поисковому запросу.

В проекте CoworkingFinder BM25 будет использоваться для определения наиболее релевантных описаний коворкингов.

При получении пользовательского запроса система выполняет его предварительную обработку и сравнивает с документами корпуса.

Для каждого документа вычисляется оценка релевантности.

При расчёте учитываются частота встречаемости терминов запроса в документе, распространённость терминов во всём корпусе и длина документа.

После вычисления оценок документы сортируются по убыванию релевантности.

В результате формируется список наиболее подходящих документов.

Количество документов, передаваемых на следующий этап обработки, определяется параметром `top_k`.

Значение `top_k` будет выбрано экспериментально при тестировании системы.

Следует учитывать, что BM25 оценивает текстовую релевантность, но сам по себе не гарантирует соблюдение всех условий пользователя, например ограничения стоимости или времени работы.

Поэтому при формировании рекомендаций необходимо дополнительно проверять соответствие найденных коворкингов указанным требованиям.

## 6. Формирование контекста для LLM

После выполнения поиска наиболее релевантные документы передаются в модуль формирования контекста.

Контекст представляет собой совокупность найденной информации, которая будет использована языковой моделью для генерации ответа.

В контекст предполагается включать:

- Исходный запрос пользователя.
- Названия найденных коворкингов.
- Описания рабочих пространств.
- Стоимость посещения.
- График работы.
- Доступные удобства.
- Идентификаторы документов.

При формировании контекста необходимо сохранять связь между информацией и документом, из которого она была получена.

Это позволит указывать источники в итоговом ответе.

Объём передаваемого контекста должен учитывать ограничения выбранной языковой модели.

## 7. Генерация ответа с использованием LLM

LLM предназначена для формирования понятного текстового ответа на основании пользовательского запроса и найденных документов.

Языковая модель получает исходный запрос и контекст, сформированный на предыдущем этапе.

В инструкции для модели должны быть определены следующие требования:

1. Использовать только сведения из предоставленных документов.
2. Учитывать требования пользователя к стоимости, расположению, графику работы и удобствам.
3. Не добавлять характеристики коворкингов, отсутствующие в источниках.
4. Объяснять, почему предложенные варианты соответствуют запросу.
5. Указывать источники использованной информации.
6. Сообщать об отсутствии подходящих вариантов, если найденные документы не позволяют удовлетворить запрос.

Ответ должен быть понятным пользователю и содержать конкретные рекомендации.

Например, для запроса о коворкинге в Москве стоимостью до 800 рублей в день с переговорной комнатой система должна предложить только те варианты, для которых в документах подтверждены необходимые характеристики.

Если найденные документы соответствуют запросу лишь частично, система должна явно указать, какие требования не выполняются.

## 8. Обработка пользовательского запроса

Работа RAG-модуля предполагает следующую последовательность действий.

**Этап 1. Получение запроса.**

Пользователь вводит текст в интерфейсе интеллектуального помощника.

**Этап 2. Передача запроса.**

Frontend отправляет текст серверной части приложения.

**Этап 3. Предварительная обработка.**

Система подготавливает запрос к поиску, применяя выбранные методы нормализации текста.

**Этап 4. Поиск документов.**

BM25 вычисляет оценки релевантности и формирует список наиболее подходящих документов.

**Этап 5. Формирование контекста.**

Система выбирает документы, необходимые для генерации ответа, и объединяет их с пользовательским запросом.

**Этап 6. Генерация ответа.**

LLM анализирует переданный контекст и формирует рекомендации.

**Этап 7. Возврат результата.**

Серверная часть передаёт сформированный ответ на frontend.

**Этап 8. Отображение результата.**

Пользователь получает рекомендации в интерфейсе интеллектуального помощника.

## 9. Обработка нестандартных ситуаций

При работе RAG-модуля необходимо предусмотреть обработку ситуаций, в которых невозможно сформировать полноценный ответ.

**Отсутствие релевантных документов.**

Если поиск не обнаружил подходящих документов, система должна сообщить пользователю об отсутствии информации.

**Недостаток данных.**

Если в найденных документах отсутствуют сведения, необходимые для ответа, система не должна самостоятельно придумывать недостающие характеристики.

**Противоречивые требования.**

Если запрос содержит условия, которым не соответствует ни один коворкинг, система должна сообщить об отсутствии подходящих вариантов.

**Некорректный запрос.**

Если пользователь отправляет пустой запрос, приложение должно предложить ввести текст.

**Ошибка языковой модели.**

Если получить ответ от LLM не удалось, система должна вывести сообщение об ошибке без нарушения работы остальных компонентов приложения.

## 10. Оценка качества RAG

Для проверки качества интеллектуального поиска планируется создать benchmark — набор тестовых запросов с заранее определёнными ожидаемыми результатами.

Benchmark будет включать вопросы различной сложности.

Примеры тестовых запросов:

1. «Найди коворкинг в Москве стоимостью до 800 рублей в день».
2. «Какие коворкинги имеют переговорную комнату?»
3. «Где можно работать после 22:00?»
4. «Подбери недорогой коворкинг в Санкт-Петербурге с Wi-Fi».
5. «Есть ли коворкинги с парковкой?»
6. «Какие пространства подходят для работы небольшой команды?»

Для каждого запроса будут определены релевантные документы и ожидаемые факты, которые должны присутствовать в ответе.

Оценка качества будет проводиться отдельно для поиска документов и генерации ответов.

### 10.1. Оценка качества поиска

Для проверки BM25 могут использоваться следующие метрики:

**Precision@k** — доля релевантных документов среди первых `k` результатов поиска.

**Recall@k** — доля найденных релевантных документов среди всех релевантных документов корпуса.

**MRR (Mean Reciprocal Rank)** — метрика, учитывающая позицию первого релевантного документа в результатах поиска.

Выбор окончательного набора метрик будет выполнен при подготовке benchmark.

### 10.2. Оценка качества генерации

Для оценки ответов LLM предполагается проверять:

- Соответствие ответа пользовательскому запросу.
- Фактическую корректность рекомендаций.
- Наличие подтверждения утверждений в найденных документах.
- Соблюдение ограничений пользователя.
- Отсутствие вымышленных сведений.
- Понятность и полноту ответа.

Результаты проверки будут использоваться для корректировки параметров поиска и инструкций языковой модели.

## 11. Параметры RAG-модуля

При реализации RAG предполагается определить и настроить следующие параметры:

**Размер корпуса документов** — количество описаний коворкингов, доступных для поиска.

**Метод обработки текста** — способ токенизации и нормализации документов и запросов.

**Параметры BM25** — значения коэффициентов алгоритма, влияющих на ранжирование документов.

**top_k** — количество документов, выбираемых по результатам поиска.

**Языковая модель** — LLM, используемая для формирования ответов.

**Формат контекста** — способ передачи найденных документов языковой модели.

**Инструкция для LLM** — правила формирования рекомендаций и использования источников.

Значения параметров будут определены на этапе реализации и уточнены по результатам тестирования.

## 12. Текущее состояние реализации

На первой контрольной точке реализован интерфейс интеллектуального помощника, позволяющий пользователю вводить текстовые запросы и получать демонстрационные ответы.

Полноценный RAG-модуль пока отсутствует.

В текущей версии проекта:

- Данные о коворкингах хранятся локально в `frontend/data.js`.
- Поиск в каталоге выполняется средствами JavaScript.
- Алгоритм BM25 не подключён.
- Языковая модель не подключена.
- Серверная обработка запросов отсутствует.
- Ответы интеллектуального помощника являются демонстрационными.
- Benchmark ещё не подготовлен.

Реализация RAG-модуля, создание поискового индекса, интеграция LLM и оценка качества запланированы на следующую контрольную точку.
