# Архитектура проекта CoworkingFinder

## Структура проекта

Проект организован в виде единого Git-репозитория, содержащего документацию, исходный код приложения, демонстрационные данные и файлы для будущего тестирования.

## 1. Корневой каталог проекта

Корневой каталог `coworking-finder/` содержит основные документы и служебные файлы, необходимые для организации разработки.

### 1.1. README.md

Основной информационный файл проекта.

Содержит:

- Название и краткое описание приложения.
- Цель разработки.
- Описание целевой аудитории.
- Перечень основных возможностей.
- Инструкцию по установке и запуску.
- Информацию о текущем состоянии разработки.
- Планируемые этапы развития.
- Распределение обязанностей между участниками команды.

README.md является первым документом, с которым знакомится пользователь или разработчик при открытии репозитория.

### 1.2. AGENTS.md

Файл с инструкциями для кодинговых ИИ-агентов, используемых в процессе разработки
Содержит правила взаимодействия с репозиторием.
Основные требования:

1. Перед изменением исходного кода необходимо изучить существующую документацию.
2. При добавлении новых возможностей следует предварительно обновить соответствующие спецификации.
3. Изменения должны соответствовать описанным пользовательским сценариям.
4. После внесения изменений необходимо проверить работоспособность приложения.
5. Информация о выполненной работе должна фиксироваться в истории изменений.

Использование данного файла позволяет обеспечить согласованность между документацией и программной реализацией.

### 1.3. CHANGE_HISTORY.md

Документ для фиксации истории разработки проекта.
В нём указываются:
- Дата внесения изменений.
- Описание добавленных возможностей.
- Информация об исправленных ошибках.
- Результаты выполненных проверок.
- Известные ограничения текущей версии.

Данный файл дополняет историю коммитов Git и позволяет отслеживать развитие проекта.

### 1.4. .gitignore

Служебный файл системы контроля версий Git.
Определяет файлы и каталоги, которые не должны добавляться в репозиторий.

Например:
- Временные файлы операционной системы.
- Служебные журналы.
- Локальные зависимости.
- Файлы окружения с конфиденциальными настройками.
- Автоматически создаваемые файлы Python.

Это позволяет поддерживать репозиторий в организованном состоянии.

## 2. Каталог spec/

Каталог `spec/` предназначен для хранения проектной документации.
Он является основой применения подхода Spec-Driven Development.
Документация разделена на два направления:
- `product/` — продуктовые требования.
- `tech/` — технические спецификации.

### 2.1. Каталог spec/product/

Содержит документы, описывающие приложение с точки зрения пользователя.

#### product.md

Спецификация продукта.

В документе описываются:
- Название приложения.
- Проблема, которую решает сервис.
- Целевая аудитория.
- Основные функции.
- Ожидаемые результаты использования.
- Ограничения первой версии.
- Критерии проверки функциональности.

#### scenarios.md

Документ, содержащий пользовательские сценарии.

В проекте рассматриваются следующие сценарии:

**Сценарий 1. Поиск коворкинга**

1. Пользователь открывает приложение.
2. Просматривает каталог рабочих пространств.
3. Указывает необходимые параметры поиска.
4. Система фильтрует список коворкингов.
5. Пользователь получает подходящие результаты.

**Сценарий 2. Бронирование**

1. Пользователь выбирает коворкинг.
2. Открывает подробную информацию.
3. Указывает дату посещения.
4. Нажимает кнопку бронирования.
5. Система отображает демонстрационное подтверждение.

**Сценарий 3. Использование интеллектуального помощника**

1. Пользователь открывает интерфейс помощника.
2. Вводит запрос на естественном языке.
3. Система обрабатывает запрос.
4. Пользователь получает ответ с рекомендациями.

### 2.2. Каталог spec/tech/

Содержит техническую документацию приложения.

#### architecture.md

Описывает:

- Общую структуру проекта.
- Назначение каталогов и файлов.
- Компоненты приложения.
- Используемые технологии.
- Взаимодействие между компонентами.
- Планируемую архитектуру системы.

#### rag.md

Содержит:

- Назначение RAG-модуля.
- Описание корпуса документов.
- Принципы использования BM25.
- Порядок взаимодействия с LLM.
- Формат ожидаемых ответов.
- Подход к тестированию и оценке качества поиска.

## 3. Каталог frontend/

Каталог `frontend/` содержит клиентскую часть веб-приложения.

- **HTML5** — структура страниц.
- **CSS3** — оформление интерфейса.
- **JavaScript** — обработка действий пользователя.

### 3.1. index.html

Основной HTML-файл приложения.
В документе определены следующие разделы:

1. Шапка сайта (Header)
2. Главный экран (Hero)
3. Каталог коворкингов
4. Интерфейс ИИ-помощника
5. Информация о проекте
6. Модальное окно коворкинга

### 3.2. styles.css

Содержит:

- Цветовую палитру.
- Настройки шрифтов.
- Размеры элементов.
- Отступы.
- Оформление кнопок.
- Стили карточек коворкингов.
- Оформление каталога и фильтров.
- Стили модальных окон.
- Оформление интерфейса помощника.
- Адаптивные стили для разных размеров экрана.

### 3.3. data.js

Файл демонстрационных данных.
Содержит массив объектов `coworkings`, каждый из которых описывает отдельное рабочее пространство.

Сейчас данные хранятся непосредственно в JavaScript-файле.

Все представленные коворкинги являются вымышленными и используются исключительно для демонстрации работы интерфейса.

В дальнейшем предполагается вынести данные в отдельное хранилище и использовать их для формирования корпуса документов RAG.

### 3.4. app.js

Основной JavaScript-файл клиентской части.
Отвечает за интерактивность приложения и обработку пользовательских действий.

В нём реализованы следующие функции.
1. Отображение каталога
2. Поиск и фильтрация
3. Просмотр подробной информации
4. Демонстрационное бронирование
5. Интерфейс ИИ-помощника

## 4. Каталог backend/

Каталог `backend/` предназначен для будущей серверной части приложения.
В каталоге находится файл `README.md`, описывающий назначение будущего компонента.

### 4.1. Планируемые функции backend

В дальнейшем серверная часть должна обеспечивать:
1. Приём запросов от frontend.
2. Получение информации о коворкингах.
3. Обработку запросов интеллектуального поиска.
4. Взаимодействие с BM25.
5. Передачу найденных документов в LLM.
6. Возврат сформированных ответов пользователю.
Дополнительно может быть реализовано хранение информации о бронированиях.

### 4.2. Планируемые технологии

В качестве возможной технологии серверной разработки рассматривается:
**Python + FastAPI.**
Окончательный выбор технологий будет осуществлён командой на следующих этапах разработки.

## 5. Каталог tests/

Каталог `tests/` предназначен для автоматизированного тестирования приложения.
В каталоге находится информационный файл `README.md`.

### 5.1. Планируемые проверки

**Тестирование интерфейса:**
- Корректное отображение каталога.
- Работа фильтров.
- Открытие карточек.
- Проверка ввода даты.

**Тестирование backend:**
- Корректная обработка HTTP-запросов.
- Проверка формата возвращаемых данных.
- Обработка ошибочных запросов.

**Тестирование RAG:**
- Проверка получения документов.
- Проверка корректности передачи контекста.
- Проверка обработки запросов без найденной информации.

## 6. Каталог benchmark/

Каталог `benchmark/` предназначен для оценки качества интеллектуального поиска.
Benchmark представляет собой заранее подготовленный набор проверочных вопросов и ожидаемых результатов.
На первой контрольной точке benchmark ещё не реализован.

### 6.1. Планируемое содержимое

В дальнейшем каталог будет содержать:
- Набор тестовых запросов.
- Эталонные релевантные документы.
- Ожидаемые факты в ответах.
- Результаты поиска BM25.
- Результаты работы RAG.
- Метрики качества.
### 6.2. Пример проверочного запроса

**Запрос:**
«Какие коворкинги работают после 22:00 и имеют переговорную комнату?»

**Ожидаемое поведение:**
1. BM25 находит релевантные документы.
2. Система анализирует найденные сведения.
3. LLM формирует ответ на основании предоставленного контекста.
4. Ответ содержит информацию о подходящих коворкингах.

## 7. Запуск приложения

Для запуска необходимо:

1. Скачать или клонировать репозиторий проекта.
2. Открыть каталог `frontend/`.
3. Найти файл `index.html`.
4. Открыть его в веб-браузере.

После запуска пользователю доступны каталог коворкингов, фильтры, карточки и демонстрационные функции.
